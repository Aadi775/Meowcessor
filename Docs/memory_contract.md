# Meowcessor Memory Contract (Baseline)

## Purpose and scope

This document defines the memory behavior for the first reliable single-core
baseline. It is intentionally smaller than the final SoC interface. The core
will use a Harvard architecture: instruction fetch and data access have
separate interfaces. A future shared interconnect may connect both interfaces
to the same physical SRAM, but that does not combine their logical channels.

## Addressing and byte order

- Addresses are 32-bit, byte addresses.
- Memory is little-endian. The byte at the lowest address is the least
  significant byte of a multi-byte value.
- Instruction fetches are 32-bit aligned and return one 32-bit instruction.
- Data accesses are byte, halfword, or word accesses (8, 16, or 32 bits).
- This baseline does not split misaligned accesses across words. Misaligned
  halfword/word accesses are unsupported and must eventually report an
  architectural exception; exception/trap handling is a later milestone.

## Harvard interfaces

### Instruction memory

- `imem_addr` is the byte address of the instruction to fetch.
- `imem_rdata` is the 32-bit instruction at that address.
- For the baseline, instruction memory is read combinationally: the instruction
  corresponding to the current address is available in the same cycle.
- Instruction memory is read-only through the core interface.

### Data memory

The baseline data path uses a 32-bit aligned word bus. The LSU presents the
effective byte address and access size; it aligns the bus word address and
selects/positions the bytes using the low address bits.

The eventual RTL interface must carry these semantics:

| Signal / property | Meaning |
| --- | --- |
| `dmem_addr` | Effective 32-bit byte address generated by the LSU |
| `dmem_re` | Assert for a load; otherwise deassert |
| `dmem_we` | Assert for a store; otherwise deassert |
| `dmem_wdata[31:0]` | Store data placed in the addressed byte lanes |
| `dmem_wstrb[3:0]` | One bit per byte lane; `1` writes that byte |
| `dmem_rdata[31:0]` | Aligned 32-bit word containing the requested load bytes |

The aligned word address is `{dmem_addr[31:2], 2'b00}`. Byte lane `i` maps to
address `aligned_address + i` and `dmem_wdata[8*i +: 8]` /
`dmem_rdata[8*i +: 8]`. The LSU uses `dmem_addr[1:0]` and the access size to
select store lanes and extract/extend load data.

For the initial simulation memory, reads are combinational and stores commit on
the rising clock edge when `dmem_we` is asserted. `dmem_re` identifies a load
request, although the simple baseline memory has no separate read-accept or
response handshake. The core must hold the effective address and store
controls/data stable through the committing edge.

## RV32I load/store behavior

| Instruction | Size | Load result |
| --- | --- | --- |
| `LB` | 1 byte | Sign-extend to 32 bits |
| `LBU` | 1 byte | Zero-extend to 32 bits |
| `LH` | 2 bytes | Sign-extend to 32 bits |
| `LHU` | 2 bytes | Zero-extend to 32 bits |
| `LW` | 4 bytes | Return all 32 bits |
| `SB` | 1 byte | Write one selected byte lane |
| `SH` | 2 bytes | Write two selected byte lanes |
| `SW` | 4 bytes | Write all four byte lanes |

Effective addresses are `rs1 + sign_extended_immediate`. The LSU is responsible
for lane selection, load extraction, and sign/zero extension. The memory model
stores bytes (or implements equivalent byte enables), not only whole words.

## Deliberate exclusions for this milestone

- Variable-latency memories and wait states.
- Request/response `ready`/`valid` handshakes, retries, and bus errors.
- Misaligned access emulation or completed trap handling.
- Caches, virtual memory, atomics, and memory protection.
- Arbitration between multiple masters. The later shared interconnect will
  define that separately while preserving the independent Harvard core ports.

## Implementation/test acceptance criteria

1. Instruction and data paths are separately observable in the testbench.
2. Testbench memory is deterministic and byte-addressable/lane-aware.
3. `LB/LBU/LH/LHU/LW` return correct values, including negative sign-extension
   cases and accesses to every byte lane.
4. `SB/SH/SW` modify only their selected bytes and preserve other bytes.
5. Aligned-access behavior is checked; unsupported misaligned accesses are
   explicitly tested once the core has an exception signal/handler.
6. Tests check architectural outcomes and fail on timeout or unexpected memory
   transactions.

## Future extension point

When adding the shared interconnect and DMA/accelerator masters, add an explicit
request/response handshake and arbitration policy. Keep the core's instruction
and data request channels separate (Harvard), even if both are routed to the
same physical SRAM. Document ordering, response timing, and error behavior at
that stage rather than assuming the current zero-wait simulation behavior.
